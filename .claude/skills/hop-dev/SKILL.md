# HOP development conventions

HOP is a no-server, no-account, proximity-first mesh photo/video and messaging app (see [../../../docs/memo.md](../../../docs/memo.md) for product context, [../../../docs/prd.md](../../../docs/prd.md) for feature-level spec/acceptance criteria/NFRs, [../../../BUILD_PLAN.md](../../../BUILD_PLAN.md) for phase sequencing, and [../../../docs/adr/](../../../docs/adr/) for architecture decisions that close specific gaps in the above). A "post" is either a photo or a short video — treat both as first-class, not video-with-photo-bolted-on. These conventions exist because this architecture has failure modes that are expensive to fix after the fact — most of this file is about catching those early.

## Invariant checks before any change lands

Treat these as blocking, not stylistic:

1. **No HOP-owned server in the content, discovery, or message-delivery path.** If a change adds a network call to any HOP-controlled endpoint for discovery, transfer, feed ranking, moderation, or message relay, stop and flag it — that's an architecture violation, not a detail to fix later. Volunteer-operated relay nodes and public DHT infrastructure are fine; anything HOP operates or controls is not. **Narrow exception:** address-only bootstrap/rendezvous nodes in `rendezvous/` (peer addresses only, zero content/topic visibility, phased out via peer exchange — [ADR 0002](../../../docs/adr/0002-bootstrap-node-carveout.md)). Don't stretch this exception to cover anything that can answer a content or topic query — that's what the exception exists to prevent.
2. **No accounts, but identity isn't free either.** No phone number/email/password field, no server-held profile, no persistent cross-device identity — but local identity is bound to a hardware attestation token (Play Integrity / App Attest), not left as free-floating soft state ([ADR 0004](../../../docs/adr/0004-sybil-resistant-identity.md)). Attestation proves "one real device," never who owns it, and needs no HOP-operated verification server, so it doesn't reintroduce an account — but faucet caps, "don't relay" signal-counting, rate limiting, and blocking all key off it. Don't implement any of those against a free/resettable local ID — that's the Sybil hole ADR 0004 exists to close. 1:1 and group chat must be startable from a post/in-person hop, never from a phone number lookup (PRD §4.3-4.4).
3. **Decay and "don't relay" are protocol-layer, not app-layer — and are enforced by keys, not politeness.** Decay is enforced by decryption-key expiry, and reach-tier limits above Locality by per-tier key-wrapping ([ADR 0003](../../../docs/adr/0003-cryptographic-decay-and-reach-enforcement.md)) — a feed-ranking flag alone doesn't stop the DHT from serving stale/out-of-tier content forever, since content-addressed storage persists independent of what the reference client chooses to show. "Don't relay" signal-counting must be gated by the attested identity + local-receipt-proof from ADR 0004, or it's trivially Sybil-able in both directions (fake abuse reports as easily as fake suppression of real content). State the limit plainly wherever this is documented or surfaced to a user: these mechanisms are a strong deterrent for the honest-client population, not an absolute guarantee against a determined custom client — see the honesty note in memo §7.
4. **Relay nodes never see plaintext.** Any code path that touches a relayed or store-and-forwarded message must operate on ciphertext only. 1:1 uses Double Ratchet; groups use per-member pairwise Double Ratchet fan-out in v1, not a full group ratchet (PRD §4.3 phasing note — a proper group ratchet over a partitioned, serverless network needs a delivery-ordering design this product doesn't have yet). Both live in `crypto/` (Signal Protocol pattern, PRD §4.3-4.4, §6; [ADR 0001](../../../docs/adr/0001-crypto-module-placement.md)) — if a change would require a relay node to decrypt to do its job, the design is wrong, not the code. Store-and-forwarded messages expire after a bounded retention window (PRD §4.4); a session that's skipped past the ratchet's skipped-key cache falls back to a fresh handshake rather than silently dropping messages.
5. **P2P/mesh mechanics stay invisible in the UI.** No exposed technical language (BLE, WiFi Direct, DHT, hop count, relay) in user-facing strings or flows — reach radius is the one mesh concept users interact with directly: chosen at first-run setup, changeable later in settings, and overridable per-post at post time without changing what the user is currently browsing (PRD §4.2, §5). Report and block are one tap from any post/message (PRD §5) — this is the safety-critical counterpart to having no account-suspension lever, don't let it get buried behind a menu during implementation.

## Build in phase order

Check [BUILD_PLAN.md](../../../BUILD_PLAN.md) before adding a feature. Don't build Phase N+2 primitives while Phase N is unfinished — e.g., no token/contract code before local mesh + relay (Phases 1-2) are solid, no DHT/internet-mode code before both platforms' local mesh works. Building ahead of the current phase tends to lock in assumptions the earlier phase would have invalidated.

## Module boundaries

Per the proposed repo structure in BUILD_PLAN.md:

- `protocol/` — wire format, relay/decay logic, geohash-tier resolution, reach-tier key-wrapping policy. This is the one thing every platform and every independent relay-node implementation must agree on. Changes here are the highest-cost-to-get-wrong; version the wire format explicitly and never break backward compatibility silently. The wire format carries an explicit content-type flag (photo vs. video) from day one (BUILD_PLAN.md decision #4) — don't infer content type from payload sniffing or file extension.
- `crypto/` — messaging encryption: Double Ratchet (1:1), pairwise fan-out for groups, decay/reach-tier key management, and device-attestation identity. Split out from `protocol/` on purpose ([ADR 0001](../../../docs/adr/0001-crypto-module-placement.md)) — it carries a different risk profile (a bug here is a plaintext-exposure incident, not a functional regression) and needs an independent security review before messaging ships. Dependency is one-way: `protocol/` depends on `crypto/` to encrypt/decrypt payloads before they hit the wire; `crypto/` never depends back on `protocol/`. A PR introducing that reverse dependency is a design smell — stop and flag it.
- `rendezvous/` — bootstrap/rendezvous nodes for cold-start peer discovery ([ADR 0002](../../../docs/adr/0002-bootstrap-node-carveout.md)). Keep this address-only by construction: no function here should be able to answer a content-hash or topic query, even indirectly. If a change would let it do that, it's no longer the narrow exception the non-negotiable carves out — stop and flag it.
- `mobile/android/`, `mobile/ios/` — platform apps. Keep platform-specific radio/background-scanning quirks (BLE limits, Multipeer Connectivity restrictions) isolated here, not leaked into `protocol/` or `crypto/`. On Android, BLE scanning uses the `neverForLocation` flag (API 31+) so peer discovery doesn't force a Location permission grant (PRD §6) — a real friction point for a privacy-positioned product; don't default to requesting `ACCESS_FINE_LOCATION` without checking whether `neverForLocation` scanning covers the use case first. The two-tab UX (feed + inbox, PRD §5) and the reach-radius control at post time are app-layer, not protocol-layer. So is posting itself in v1 — it's a media-library picker, not a camera (PRD §4.1, §8); don't build camera/viewfinder UI until in-app capture is actually prioritized, and when it is, it's still purely app-layer (feeds the same upload/post pipeline) with no `protocol/`/`crypto/` dependency.
- `dht/`, `contracts/`, `tools/relay-node/`, `tools/preseed/` — later-phase modules; don't add dependencies on these from Phase 1-3 code paths.

## Reach radius / geohash tiers

PRD §4.2 fixes the mechanism: Locality (~100m mesh) → Town → City → Country map to increasing geohash-prefix precision used as the DHT topic-subscription key. Keep the tier-to-precision mapping in one place in `protocol/` (not duplicated per platform) since it's part of what every peer must agree on to resolve reach correctly. Locality must always resolve via BLE/WiFi Direct alone — never gate it behind a DHT/internet-mode lookup (PRD §4.2 acceptance, §7 NFR). Resolve topic membership against the target geohash cell **plus its neighbor cells**, not an exact-cell match — geohash cells have hard edges, so two peers 10m apart on either side of a boundary would otherwise land in different tiers.

Reach-tier restriction above Locality is enforced by per-tier key-wrapping (ADR 0003), not by topic-key secrecy — geohash-prefix topics aren't secret, so anything gated only by "don't subscribe to topics outside your tier" is scraper-bait, not a boundary. When implementing tier resolution, the acceptance bar is "the reference client only decrypts for peers with a valid tier claim inside the decay window," not "content outside the tier is unreachable" — don't write code or docs that imply the stronger claim.

It's one radius value, not two: the same setting is both the default reach for a user's own posts and the zoom level of their browse feed. It's set once at first-run setup, changeable later in settings, and overridable per-post at post time — a per-post override changes that post's reach only, not what the user is currently browsing. Don't build separate "browse radius" and "post radius" state; there's one radius plus an ephemeral per-post override.

## Testing approach for mesh/P2P code

- The hard case is **low-density, near-broken mesh** (a relay chain one hop from failing), not the dense-venue happy path — the memo's own org design assigns a QA role specifically to stress-test this. Prioritize tests here over adding more happy-path coverage.
- Prefer integration tests that simulate multiple peers with realistic radio constraints (limited range, intermittent connectivity, asymmetric discovery) over unit tests that mock the transport layer entirely — mocked transport tests won't catch the failure modes that matter for this product.
- Any change to `protocol/` needs a cross-version compatibility test once more than one wire-format version exists.
- Hold changes to the NFRs in PRD §7 to a measured, not assumed, bar: local WiFi Direct transfer in low single-digit seconds for a compressed clip, locality tier fully functional offline, message delivery near-instant in-range/online with store-and-forward delay acceptable only when a party is offline, and discovery-scanning battery drain within each platform's background-execution limits (iOS in particular — don't design around ambient background discovery there).
- Ratchet/encryption code needs test vectors covering forward secrecy after simulated device compromise and out-of-order/dropped message delivery (expected under store-and-forward), not just the happy-path encrypt/decrypt round trip. Include a test for exceeding the skipped-message-key cap — the session must fall back to a fresh handshake, not silently lose messages.
- Decay/reach-tier key-expiry code (ADR 0003) needs tests for the actual failure mode this exists to prevent: a client holding an expired key must not be able to decrypt, and a client without a valid tier claim must not receive the unwrap key — test the negative case, not just "a valid client can still decrypt."
- Attested-identity-gated code (ADR 0004: faucet caps, "don't relay" counting, rate limiting, blocking) needs a test for the Sybil case it's meant to close — e.g. that N fake/reset identities without distinct attestations don't add up to N counted toward a threshold.

## Extra scrutiny areas

These touch safety, money, privacy, or irreversible protocol decisions — hold changes here to a higher bar and prefer a second pair of eyes:

- On-device hash-matching / content moderation logic (Phase 5), including the receipt-side re-check (PRD §4.6) — don't let this regress to send-side-only, since that's the exact bypass a modified client would use.
- Anything in `crypto/` (Double Ratchet, group fan-out, decay/reach-tier key management, device attestation) and anything in `protocol/` that determines what a relay node can observe or what key-distribution decisions get made — a bug here is a plaintext-exposure, content-persistence, or Sybil-farming incident, not a functional regression. Needs independent security review before Phase 1 messaging/identity ships, per ADR 0001 and ADR 0004.
- Anything in `contracts/` — the token is transfer-restricted by design; a change that weakens that restriction is a regulatory exposure, not just a bug (memo §6, §10). Contract governance is a time-locked multisig with no pause/freeze/blacklist power over user balances (memo §6) — a PR adding that capability is a design violation, not a feature request.
- NAT traversal / relay-node trust logic (Phase 4) — volunteer-operated infrastructure means you can't assume relay nodes are honest.
- `rendezvous/` (ADR 0002) — any change that would let a bootstrap node observe or answer content/topic queries needs a second pair of eyes; that's the one thing this module must never do.
- Legal-gated work: anything touching the rights-holder hash-block channel (memo §7, copyright/secondary-liability exposure) needs Trust & Safety/Legal sign-off before shipping, not just an engineering review — gated by outside counsel, per BUILD_PLAN.md Phase 5. Illegal-content *reporting* obligations (e.g. CSAM/CyberTipline, memo §7) are a separate, deferred item — tracked but not yet gating current work; don't block on it, but don't quietly build something that forecloses the eventual answer either (e.g. avoid baking in assumptions that no reporting mechanism could ever exist).
