You are implementing HOP, a serverless, proximity-first short-form photo/video and messaging app. A "post" is either a photo or a short video — treat both as first-class content types, not video-with-photo-bolted-on. v1 posting is upload-from-device-media only; in-app camera capture is a planned future, app-layer-only addition (PRD §4.1, §8) with no protocol dependency — don't build it now, and don't gate anything else on it. Read [CLAUDE.md](../../CLAUDE.md), [docs/memo.md](../../docs/memo.md), [docs/prd.md](../../docs/prd.md), [BUILD_PLAN.md](../../BUILD_PLAN.md), and [docs/adr/](../../docs/adr/) before starting if you haven't already — the PRD carries the feature-level acceptance criteria and NFRs, the memo and BUILD_PLAN carry the constraints and phase sequencing, and the ADRs close specific architecture gaps referenced throughout this file (0001 crypto module placement, 0002 bootstrap-node carve-out, 0003 cryptographic decay/reach-tier enforcement, 0004 Sybil-resistant identity).

## Non-negotiable constraints

- No HOP-owned server ever sits in the content, discovery, or message-delivery path. Volunteer-operated relay nodes and public DHT infrastructure are fine; anything HOP operates or controls is not. **Narrow exception:** address-only bootstrap/rendezvous nodes in `rendezvous/` — peer addresses only, zero content/topic visibility, phased out via peer exchange once a device has any live peer (ADR 0002). Don't extend this exception to anything that can answer a content or topic query.
- No accounts, no server-held profile, no persistent cross-device identity — but local identity is bound to a hardware attestation token (Play Integrity / App Attest), not left free-floating (ADR 0004). Attestation proves "one real device," never who owns it, and needs no HOP-operated verification server. This exists because faucet caps, "don't relay" signal-counting, rate limiting, and blocking are all meaningless against a free/resettable identity — implement all four against the attested key, not a soft local ID. 1:1 and group chats are startable only from a post or in-person hop, never from a phone number or server-side lookup (PRD §4.3-4.4).
- Ephemeral decay and community "don't relay" propagation control are protocol-layer primitives, designed in now, not retrofitted after the fact — this architecture cannot cheaply add takedown/safety behavior later, so treat it as load-bearing from the first line of relay code. Decay is enforced by decryption-key expiry, not client politeness — content-addressed DHT storage persists a clip's ciphertext regardless of what the feed shows, so decay only means something if honest clients actually stop distributing the unwrap key past the window (ADR 0003). "Don't relay" signal-counting must be gated by attested identity + local-receipt-proof (ADR 0004) or it's Sybil-able in both directions — as easy to weaponize for false suppression as to rely on for real abuse response.
- Messaging is end-to-end encrypted such that no relay node can ever read plaintext: Double Ratchet for 1:1; groups use per-member pairwise Double Ratchet fan-out in v1, not a full group ratchet (PRD §4.3 — a serverless group ratchet with consistent membership needs a delivery-ordering design this product doesn't have yet, don't treat it as a drop-in). Both live in `crypto/` (Signal Protocol pattern, PRD §4.3-4.4, §6; ADR 0001). Forward secrecy must hold even after a simulated device compromise. Store-and-forwarded messages expire after a bounded retention window; a session that exceeds the ratchet's skipped-key cache falls back to a fresh handshake rather than silently losing messages. If a design would require a relay to decrypt to do its job, stop — that's a protocol design flaw, not an implementation detail.

## Feature-level specifics from the PRD

- **Reach radius (§4.2):** Locality (~100m mesh) → Town → City → Country tiers map to increasing geohash-prefix precision used as the DHT topic-subscription key, resolved against the target cell **plus its neighbor cells** (avoids boundary-edge misses between adjacent cells). Locality must resolve entirely offline via BLE/WiFi Direct — never route it through a DHT/internet-mode lookup. Above Locality, reach-tier limits are enforced by per-tier key-wrapping (ADR 0003), not by topic-key secrecy — geohash prefixes aren't secret, so implement and describe this as "the reference client only decrypts within your tier and the decay window," never as an absolute access-control guarantee. It's a single radius value, not separate browse/post settings: chosen at first-run setup, changeable in settings, overridable per-post at post time without affecting what's currently browsed. Don't implement it as two independent pieces of state.
- **NFRs (§7):** WiFi Direct video transfer in low single-digit seconds for a compressed short clip; photo transfer near-instant (much smaller payload, don't treat it as needing separate throughput de-risking); discovery-scanning battery drain must respect each platform's background-execution limits (iOS notably — design for "open app to see what's nearby," not ambient background discovery); locality-tier post/view must work with zero internet connectivity; message delivery near-instant in-range/online, with store-and-forward delay acceptable only when a party is offline. On Android, scan with the `neverForLocation` flag (API 31+) rather than defaulting to `ACCESS_FINE_LOCATION` — peer discovery doesn't need actual location, and requiring that permission undercuts the product's own privacy positioning.
- **Trust & safety hooks that are protocol-layer, not app-layer (§4.6):** on-device hash-matching checked on both send and receipt (catches a modified client that skips its own outbound check), a "don't relay" signal gated by attested-device count + local-receipt-proof, per-device broadcast rate limiting backed by the same attestation, and local non-identity-linked peer-reputation scoring so misbehaving devices get deprioritized without a central ban list. State the limit of all of this plainly if you're writing anything user-facing or documentation-facing: it binds the stock client, not a determined custom one.

## How to work

- Check BUILD_PLAN.md's phase list before adding anything — implement the current phase's scope, don't reach ahead into a later phase's primitives (e.g. no token/contract touches, no DHT code while local mesh is still unproven).
- Keep platform-specific quirks (Android BLE background-scanning limits, iOS Multipeer Connectivity restrictions) isolated in the platform module (`mobile/android/`, `mobile/ios/`); anything that goes in `protocol/` (wire format, decay/relay logic, geohash-tier resolution, reach-tier key-wrapping policy) or `crypto/` (Double Ratchet, group fan-out, decay/reach-tier key management, device attestation) has to be agreed by every platform and every independent relay-node implementation, so treat changes there as high-cost and version them explicitly. The two live in separate modules on purpose (ADR 0001) — `protocol/` may depend on `crypto/` to encrypt/decrypt payloads before they hit the wire, never the reverse; a PR adding that reverse dependency is a design smell, stop and flag it. The wire format carries an explicit content-type flag (photo vs. video, BUILD_PLAN.md decision #4) — don't infer type from file extension or payload sniffing.
- Posting is a media-library picker in v1, not a camera (PRD §4.1, §8) — don't build shutter/viewfinder UI now. When in-app camera capture does get built, it's still app-layer only, feeding the same upload/post pipeline; it has no `protocol/` or `crypto/` dependency and isn't pinned to any BUILD_PLAN phase, so don't block other work on it or treat it as implicitly in scope for a given phase.
- Keep `rendezvous/` (ADR 0002) strictly address-only by construction — no function there should be able to answer a content-hash or topic query, even indirectly. That scope discipline is what makes the bootstrap-node exception to the "no HOP server" constraint defensible; erode it and the exception stops being narrow.
- For mesh/relay code, prioritize testing the low-density, near-broken-chain case over the dense-venue happy path — that's the failure mode that actually breaks this product in the field. If a task touches WiFi Direct connection/session handling, remember the N-peer dense-venue case (5-20 simultaneous devices) is explicitly under-tested until the Phase 0 spike lands — don't assume the 2-device-pair happy path generalizes.
- For encryption code, test forward secrecy after simulated compromise and out-of-order/dropped delivery (expected under store-and-forward) — not just the happy-path encrypt/decrypt round trip. Include the skipped-key-cap-exceeded case (must fall back to re-handshake, not drop messages).
- For decay/reach-tier code, test the negative case explicitly: a client holding an expired key must fail to decrypt, and a client without a valid tier claim must not receive the unwrap key. For attested-identity-gated code (faucets, "don't relay" counting, rate limits, blocking), test that N fake/reset identities without distinct attestations don't count as N toward any threshold.
- Keep P2P/mesh mechanics out of anything user-facing (strings, error messages, UI copy) — BLE, WiFi Direct, DHT, hop count, and relay are implementation details the PRD requires stay invisible (§5); reach radius is the one mesh concept exposed to the user, and only as a single control at post time. Device attestation is silent background plumbing, not a user-facing prompt, except a fallback message on devices that fail attestation.
- Don't imply a stronger guarantee than the architecture provides: decay, reach-tier limits, and moderation controls bind the stock client and raise the cost of abuse — they don't make abuse by a determined custom client impossible. Say so in code comments, error strings, or docs you write for these surfaces, rather than letting "visible only to..." language stand uncorrected.
- If a task would require adding a HOP-owned network endpoint (beyond the narrow `rendezvous/` exception above), or persistent server-held user identity, stop and flag it rather than implementing it — that's an architecture violation, not an implementation detail to smooth over.
- Anything touching a rights-holder hash-block channel is legal-gated (memo §7, copyright/secondary-liability exposure, BUILD_PLAN.md Phase 5) — implement the mechanism if asked, but flag that it needs Trust & Safety/Legal sign-off before shipping, don't treat engineering completion as launch-ready. Illegal-content *reporting* obligations (CSAM/CyberTipline) are a separate, deferred item — tracked, not currently gating; don't block a task on it, but flag if a design choice would foreclose a reporting mechanism later.
- Flag (don't silently resolve) any open decision from BUILD_PLAN.md's "Open decisions before Phase 0" list, or from the PRD's own "Open Questions" (§9) — including the still-open rooted/de-Googled-device attestation-failure question (ADR 0004) — that a task depends on but hasn't actually been settled yet.
